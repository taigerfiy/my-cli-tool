# 竞彩情报匹配

输入一份竞彩清单 → 从 Base1 取已完赛的 L1–L6 → 从 001 文档取赛前 L1D →（可选）并入外部采集的 L7 → 输出一份 Markdown，供人工转交给分析 agent。

**只取数，不做任何方向判断、概率预测或投注建议。**

本 Skill 与 `football-match-data-collector` 是两个独立 Skill：后者联网抓外部情报，本 Skill 读 Base1 与 001 文档并负责汇合。边界与契约见 [references/merge-external.md](references/merge-external.md)。

## 快速开始

```bash
# 纯库内
python3 scripts/match_pack.py <清单.json> --date <YYYY-MM-DD> --out <输出.md>

# 库内 + 001 赛前文档 + 外部
python3 scripts/parse_001.py --tables <7表格.pdf> --history <历史战绩.pdf> \
  --date <YYYY-MM-DD> --out <001.json>
python3 scripts/match_pack.py <清单.json> --date <YYYY-MM-DD> --out <输出.md> \
  --doc <001.json> --external <facts.json> <match_intel_*.md> ...
```

清单 JSON（字段只需 `no` / `home` / `away`，联赛与让球自动从主表取）：

```json
[{"no":"周一006","home":"德国","away":"荷兰","rg":"-1"}]
```

`--date` 是**销售日期**（竞彩编号所属日期，不是开赛日；次日凌晨场仍算当天）。超 20 页时脚本返回非 0 并提示按场次拆包。

页数预算：纯库内单场约 3 页（8 场约 18–20 页）；含 L7 单场 3.5–3.8 页（2 场 7.4 页）；再加 L1D 后单场约 6 页（实测 2 场 12.0 页），**含 L1D+L7 时一批建议不超过 3 场**。

## 触发口令（用户口头说法 → 本 Skill 动作）

用户可只用极简口令，不必报队名、联赛、让球、文件路径；给不出的一律按下面默认解析。

| 口令 | 解析出的动作 |
|---|---|
| `情报 <日期> <编号…> [截点HH:MM]` | 全流程：001 文档解析（L1D）→ 调 `football-match-data-collector` 采集 → 校验 facts → 本 Skill 合包（L1D+L7）→ 交付 011 主 + 016 副本 |
| `采 <日期> <编号…>` | 只跑外部采集，产单场情报包 MD + facts JSON，不读 Base1 |
| `合包` | 继承当前会话上一批的清单与外部产物，跑本 Skill 合成一份包 |
| `合包 --full` | 同上，但不瘦身（保留外部盘口的描述性段落），页数会明显增加 |
| `校验` | 只跑 `validate_intel.py` |
| `回归` | 只跑 `tests/run_regression.py`，退出码非 0 即视为能力退化，停下不上新批次 |
| `拆包` | 按场次分组，一包不超过 3 场（含 L1D+L7）或 8 场（纯库内） |

解析规则：

- 编号只给后三位即可（`006`），`周二` 可省略——`<日期>` 已确定星期，统一键由此推出。
- 截点省略时按「现在」取，但不得晚于开赛时间；给了截点就全程只用这一个。
- `/` 分隔或空格分隔的多场算同一批；超过 3 场且含 L1D+L7 时先按 `拆包` 处理。

## 取数层（L1–L7 + L1D）

| 层 | 取什么 | 命中方式 |
|---|---|---|
| L0 归一 | 别名→规范名 | 名称对照表，仅当主表队名与清单不一致时兜底 |
| L1 本场 | 主表本场字段 + 001 赛前静态 + 006 终盘 | 统一键 `YYMMDD-周XNNN` 命中主表 → 取 link 的 record id → `+record-get` 读 001/006 |
| L1D 赛前文档 | 001 文件夹的 7 表格 + 历史战绩（**Base1 只存已完赛，赛前数据只能从这里来**） | `--doc` 传入 `parse_001.py` 产物，按竞彩编号对齐；与 L1 并列，冲突标 `[源冲突]` |
| L2 球队 | 球队画像（该队该主客）+ xG画像 + 近10场同主客 | 画像键 `队名\|主场`、`队名\|客场`；近10场从赛果表按日期倒序取 10 |
| L3 交锋 | 交锋次数/主队胜率/场均总进球/最近比分/样本等级 | 交锋键 `主队\|客队` |
| L4 基线 | A级联赛统计（该联赛）+ 玩法分布（该联赛各赔率档） | 联赛字段直查；玩法分布取 维度=联赛 且 维度值=该联赛 |
| L5 特征 | 本场落桶 + 该桶历史结果分布 | 由 001 的身价比/评分差/控球率差算出桶，再按 桶 查历史分布 |
| L6 质量门 | 每场标注 001/006 是否关联、各层缺口、口径断点 | 逐场生成 |
| L7 外部 | 外部 facts（伤停/人员变动）+ 阵容 + 盘口（数值表+三方对照）+ 环境 + 缺口 | `--external` 传入 facts JSON 与情报包 MD，按竞彩编号匹配 |

**赛前数据的来源顺序**：001 文档（L1D，赛前主数据）→ 外部采集（L7，只补伤停/阵容/盘口/环境）。Base1 的 L1–L6 只对已完赛场次生效；赛前查不到是设计如此，不是缺口。

口径：**近10场取同主客**（主队只算主场、客队只算客场），排除本场及以后；多场汇总一包，不按场拆分文档。

### L7 的三条硬规则

1. **赛前未入库仍入包**：Base1 主表只存**已完赛**数据，赛前场次本来就不在主表，这是设计如此、不是数据缺口。L1–L6 明写「赛前未入库（设计如此），本节不适用，不计缺口」，L7 照常渲染；不伪造历史。旧版会整场跳过，接 `--external` 后不再丢场。
2. **两源冲突并列**：库内 006 初赔与当场竞彩 SP 等不一致时，两值并列标 `[源冲突]`，不自动择一。
3. **缺口语义不换算**：L6 是库内命中情况，L7 的 `completeness` 是外部必采 12 项完成度，两者并列呈现，不合成总分。

## 国家队的特殊处理

联赛属国家队赛事时，画像/xG/交锋/联赛基线**统一标「本层不适用」而非缺口**，历史改从国家队赛果库取近10场（不分主客）。判定规则与队名映射见 `references/schema.md` 的「国家队分支」。

国家队场次同样适用「赛前未入库」，赛前数据以 L1D（001 文档）为主、L7 补伤停/阵容/盘口；Base1 只在赛后提供近10场。

## 输出质量要求

- 每层都要带样本数与区间，「—」表示该层无值，不要用估算填补
- 样本 <10 的结果标 `⚠样本不足`
- A级联赛统计引用必须带「口径」字段（该表口径非竞彩口径）
- 缺 006 时写「库内无 006 关联」；赛前场次在主表查不到，写「赛前未入库（设计如此）」，不要写成「未命中」或「缺口」
- L7 未接入时写「未提供外部数据」，不要留空

## 表结构、键格式与踩坑

读 `references/schema.md`：表 id、字段名、四种键格式、特征桶档位、10 条实测数据坑（尤其：001 必须走 link 的 record_id；record-get 字段顺序以返回体 fields 为准；两种 filter 语法不通用；data-query 的 sort 不能用 alias）。
